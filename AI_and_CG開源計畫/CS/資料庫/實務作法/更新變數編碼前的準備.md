## 1. 先備份原本的 SP 定義

萬一新版有問題，要能回滾。在目標環境執行：

```sql
-- 備份兩個 procedure 的當前定義，存成檔案後再執行 DROP
SHOW CREATE PROCEDURE explode_to_temp\G
SHOW CREATE PROCEDURE get_material_requirements_source\G
```

複製 `Create Procedure` 欄位的內容存檔。

## 2. 確認目標環境的字元集設定

```sql
SHOW VARIABLES LIKE 'character_set_%';
SHOW VARIABLES LIKE 'collation_%';
```

特別看 `character_set_database`、`character_set_connection`。如果 `character_set_database` 是 `latin1` 或 `utf8mb3`，就證實了「中文 SKU 失敗」的推測；同時也代表 **匯入這份 SQL 時 client 連線本身必須是 utf8mb4**，否則 `CREATE PROCEDURE` 內含的中文註解（`-- 檢查是否有 BOM` 等）會被破壞：

```sql
SET NAMES utf8mb4;   -- 執行新 SP SQL 前先下這一行
```

或在 client 端：MySQL Workbench 的 connection 設 `Default Schema Charset=utf8mb4`；命令列加 `--default-character-set=utf8mb4`。

## 3. 確認相關資料表本身就是 utf8mb4

SP 變數改成 utf8mb4 後，會跟 `bom_header.parent_sku`、`products.sku`、`orders.product_sku` 做 JOIN。如果這些欄位**本身**不是 utf8mb4，仍會撞 "Illegal mix of collations"：

```sql
SELECT TABLE_NAME, COLUMN_NAME, CHARACTER_SET_NAME, COLLATION_NAME
FROM INFORMATION_SCHEMA.COLUMNS
WHERE TABLE_SCHEMA = DATABASE()
  AND TABLE_NAME IN ('bom_header','bom_detail','products','orders')
  AND COLUMN_NAME IN ('parent_sku','child_sku','sku','product_sku');
```

如果有任何一筆不是 `utf8mb4_*`，光改 SP 沒用，**必須先把對應欄位 / 表也轉成 utf8mb4**：

```sql
ALTER TABLE bom_header  CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE bom_detail  CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE products    CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE orders      CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
```

> ⚠️ `CONVERT TO CHARACTER SET` 是重寫整張表的物理檔案，**大表會鎖表 / 寫 binlog**，建議離峰時段做、且事前 dump 備份。

## 4. 確認執行帳號有 `ALTER ROUTINE` 權限

```sql
SHOW GRANTS FOR CURRENT_USER();
```

需要 `ALTER ROUTINE` 才能 DROP；需要 `CREATE ROUTINE` 才能 CREATE。一般 root / 應用帳號通常都有，但託管環境（cloud RDS）有時會限制。

## 5. 停止任何「正在跑」的呼叫

`get_material_requirements_source` 如果被 cron / 排程 / 使用者畫面正在跑，DROP 那一瞬間會：
- 等到該 session 結束才會真正 drop（被 metadata lock 卡住）；
- 期間其他連線會卡在等待；
- 若超過 `lock_wait_timeout` 會 fail。

部署前確認沒有人在跑該功能；或在離峰時段做。

## 6. 注意 DROP / CREATE 的順序（依賴關係）

`get_material_requirements_source` 內部會 `CALL explode_to_temp(...)`，所以順序是：

```
1) DROP PROCEDURE get_material_requirements_source   ← 先 drop 上層
2) DROP PROCEDURE explode_to_temp                    ← 再 drop 被呼叫者
3) CREATE PROCEDURE explode_to_temp                  ← 先建被呼叫者
4) CREATE PROCEDURE get_material_requirements_source ← 最後建上層
```

我給的那份 SQL 是 `explode_to_temp` 先 CREATE、`get_material_requirements_source` 後 CREATE，順序正確。MySQL 允許「上層 SP 編譯時被呼叫者不存在」，但養成依賴順序的習慣比較穩。

## 7. 確認 MySQL 版本

- `utf8mb4` 需要 MySQL **5.5.3+**
- `CREATE TEMPORARY TABLE` 內欄位指定 `CHARACTER SET` 在所有支援 utf8mb4 的版本都可
- 確認版本：`SELECT VERSION();`

## 8. 包成交易？不行

`DROP PROCEDURE` / `CREATE PROCEDURE` 是 **DDL**，會 **隱式 commit**，不能用 `START TRANSACTION ... ROLLBACK` 回滾。所以才需要先備份（第 1 點）。

## 9. 部署後立刻驗證

按這個順序測：

```sql
-- 9a. 確認 SP 已建立
SHOW PROCEDURE STATUS WHERE Db = DATABASE()
  AND Name IN ('explode_to_temp','get_material_requirements_source');

-- 9b. 確認參數字元集已是 utf8mb4
SELECT SPECIFIC_NAME, PARAMETER_NAME, DTD_IDENTIFIER, CHARACTER_SET_NAME
FROM INFORMATION_SCHEMA.PARAMETERS
WHERE SPECIFIC_SCHEMA = DATABASE()
  AND SPECIFIC_NAME IN ('explode_to_temp','get_material_requirements_source');
-- 預期 input_sku / current_sku 對應的 CHARACTER_SET_NAME 是 utf8mb4

-- 9c. 拿一個英數 SKU 跑（先確認沒搞壞既有功能）
CALL get_material_requirements_source('2026-06-10', '', 0, 5);

-- 9d. 再拿一個中文 SKU 跑（驗證本次目標）
CALL get_material_requirements_source('<有中文 SKU 訂單的出貨日>', '', 0, 5);
```

## 10. 回滾方式

如果新版出問題：

```sql
DROP PROCEDURE IF EXISTS get_material_requirements_source;
DROP PROCEDURE IF EXISTS explode_to_temp;
-- 然後貼回第 1 步備份下來的 SHOW CREATE PROCEDURE 內容
```

---

**最容易踩雷的兩個**：第 2 點（client 連線沒設 utf8mb4 → 中文註解被亂碼存進 SP 定義）、第 3 點（表本身還是 utf8mb3 → 改了 SP 也沒用）。這兩個建議部署前一定要先檢查。
