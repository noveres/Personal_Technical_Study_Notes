**程式的本質 = 數據 (Data) + 函數 (Function)**
任何複雜的軟體系統、遊戲迴圈或企業架構，都可以拆解為資料的「輸入、處理、輸出」，以及判斷是否需要保存「儲存」
也就是狀態的轉移
## IPOS 模型四核心架構

| **階段**              | **核心關注點**                                    | **實際場景舉例**                                            |
| ------------------- | -------------------------------------------- | ----------------------------------------------------- |
| **I**nput (輸入)      | • 從哪裡拿？<br>• 拿哪些東西？<br>• 怎麼拿？<br>• 需求沒講什麼    | 協定、事件機制、調用甚麼接口                                        |
| **P**rocessing (處理) | • 需要跑哪些邏輯？<br>• 怎麼做防禦性驗證<br>• 狀態該如何轉換？       | 1. 拿到資料後，要不要驗證<br>2. 要不要渲染到畫面上、要拆成幾個步驟渲染、先繪製什麼把資料送去哪裡 |
| **O**utput (輸出)     | • 最後要的結果格式是什麼？<br>• 處理完要送去哪裡？<br>• 要不要渲染<br> | 1. 回傳成功/失敗 JSON 給前端<br>2. 繪製畫面                        |
| **S**torage (儲存)    | • 處理前後的狀態保存在哪？<br>• 讀寫的效能與資料一致性如何？           | 狀態是否需要寫入硬碟或資料庫、保存的形式是哪一種文件、字串是否需要拆分                   |

舉例：
### 做漢堡的流程

```
 分析目標 ( 知道要做什麼 ) -> 拿到食材 ( 輸入 ) -> 組合起來 ( 處理 ) -> 送單 ( 輸出 )
```


### 分析目標

我們在一切開始前，要先知道需求是什麼
在廚房還沒開火、食材還沒買之前，如果老闆只說一句：「我們來賣漢堡吧！」 身為聰明的廚師，你不能馬上衝去廚房，你要先抓出**沒明說的需求**：
例如：
- **「我們是要賣給誰？」** ：如果是開街角早餐店，你只要用小煎盤慢慢煎；但如果是要開麥當勞供應全台灣，你就得設計一條流水線。
- **「點餐能不能客製化」** ：如果客人說他對花生過敏、或是不吃香菜，你的廚房有沒有制度可以攔住，不讓員工把不該加的東西放進去。
- **「這漢堡到底怎麼疊？」** ：是麵包夾肉？還是肉夾麵包？順序錯了，生菜會被剛出爐的肉餅燙爛，客人拿到的就會是一團麵包被生菜汁泡爛的漢堡。

分析完後，老闆說：「我們要幫一家固定套餐的漢堡店寫程式，**只賣一種漢堡、需要量產、食譜拿到了！**」 好，目標明確，我們進廚房！

### 拆成這四個步驟：

### 1. Input (輸入) = 廚房備料

**「從哪裡拿哪些東西、怎麼拿」**

在動手做漢堡前，你得先把東西整齊擺在桌上。！
- **拿什麼：** 麵包、肉餅、番茄醬。
- **怎麼拿：** 從冰箱需要的東西搬出來。


### 2. Processing (處理) 

**「這個食材需要跑哪些流程」**

備料都齊了，廚師站在桌子前

- **檢查食材：** 肉餅有沒有壞掉或是夾生？訂單是不是怪怪的？
- **狀態改變：** 生肉餅 $\rightarrow$ 放到煎焙器 $\rightarrow$ 變成**熟肉餅**。
- **組裝：** 麵包 $+$ 熟肉餅 $+$ 番茄醬 $=$ 一個完整的漢堡。

###  3. Output (輸出) = 熱騰騰出餐

**「最後要的結果，以及送去哪裡」**
漢堡做好了，要送到它該去的地方。
- **要的結果：** 一個用防油紙包好、貼上餐點標籤。
- **送去哪裡：** 放在出餐檯上，讓服務生端給 3 號桌的客人。
    
###  4. Storage (儲存) = 翻開帳本記帳

漢堡送出去後，餐廳得留下紀錄，不然到了月底會不知道賺多少錢。
- **做什麼事：** 帳本寫上「賣出一個漢堡」、冰箱庫存的肉餅數量減一。
